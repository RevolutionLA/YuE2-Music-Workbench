## 一、本轮最重要的一条：假死击杀是真的，而且代码里就有一条红线违规

**B-3 成立，P1，级别维持。** 一手证据：

- `app.py:2065` `_GPU_SEM = threading.Semaphore(1)`（线程锁，不是 asyncio 锁）。
- `app.py:3908` 在 `async def rvc_pitch_analyze` 里 `with _GPU_SEM:`——`threading.Semaphore` 的 `__enter__` 会**阻塞整个事件循环**直到拿到锁。同一段代码里 `run_in_threadpool` 用得很勤（`_stream_upload_to`、`_rvc_f0_of_audio` 都在线程池），偏偏**等锁这一行留在了事件循环上**。本项目自己写的红线就是"async def 里禁止做重活"，这条违规不在重活上，在**等锁**上，后果一样：等锁期间 `/api/system/info`、`/api/tasks/unified`、健康探测全部没人应答。
- 后果链（裁定人实读 `runtime/data/logs/watchdog.log` 第 757–771 行）：今天 10:08:51→10:09:19 网关连续 27 次短探无回话，其间看门狗两次写下"仍有进程 27472 在监听、本机长任务 340/354 秒前还在推进（batch_state.json）——判为整机被占满而非假死，本轮不击杀"，**第三次（10:09:22）它击杀了 PID 27472 并重新拉起**。也就是说：当时确实有一个批量任务在跑，网关被判定假死并被杀掉。

裁定人对归因的保留：**不把 10:09 那次误杀全部记在 B-3 头上**。同一段日志显示当时机器也可能整体饱和（本机散热与驱动有既往故障记录），事件循环被冻住与整机被占满在"探测无回话"这个表象上不可区分。但 B-3 这条**代码缺陷本身成立且不依赖归因**：只要有人在一首歌正在生成时点 ⑨ 的「分析音高」并需要排队等锁，网关就会假死到看门狗的 90s 深探超时，而看门狗的"长任务判活"豁免只在 `batch_state.json` 的 mtime 新鲜时生效——**单首生成、RVC 训练、换声都不在那个文件的判据里**。这条必须按红线修掉，不是优化项。

整改：把等锁也放进线程池（`await run_in_threadpool(_gpu_sem_acquire, timeout)`，拿不到锁就明确回话"前面还有任务在占 GPU，已等待 N 秒"），或改用 `asyncio.Semaphore` 并在两个持有方统一。顺带给 ⑨ 的分离/分析加一条：等待期间每 15s 把状态写进 job，让"在等锁"在 ⑪ 上看得见。
