## 一、上一轮 F1 / F2 / F3 已修复（实测）

### F1 静音门内存
抽出 `_frame_db()` 分块计算（块 4096 帧），逐样本增益也分块落值。同一输入的峰值复测：

| 音频时长 | 修复前 | 修复后 |
|---|---|---|
| 221 s | 391 MB | **96 MB** |
| 600 s | 1061 MB | **231 MB** |
| 1200 s | （未测，原趋势 ~2.1 GB） | **445 MB** |

剩下的增长是**必需的**：输入数组与逐样本增益输出各占 4 B/采样点（600 s 约 106 MB × 2）。
算法自身的临时内存已从 `O(帧数 × 窗长)` 降到 `O(块 × 窗长)`，即 20 MB 量级。认账。

### F2 / F3
- `rvc_cancel` 改为 `_rvc_job_purge(rid)`，与 `generate_delete` 共用带 `.`/`..` + `resolve` 的守卫。
- `generate_delete` 现在先查 RVC 任务状态：`running` → 409；`pending` → 先 `_rvc_cancel(rid)` 出队再删目录。

## 四、新发现

### G1（P1）带分离的换声 ETA 高估约 3.8 倍 —— 系数取自被并发污染的样本

`static/index.html:2718`：

```js
const total = Math.max(20, sep ? 20 + 3.75 * dur : 15 + 1.0 * dur);
```

注释写着"只有 1 次实测（221 s 的歌整条 828 s ≈ 3.75×时长）"。**那条 828 s 就是三任务并行跑出来的**
—— 见第一节的对照组：三条 01:44 提交、落盘只差 27 s，各自 786/807/828 s，三条同时在抢 GPU。

而这两条**干净串行**的实测是同一首 221.1 s 的歌：**222.0 s 和 226.4 s，即 ≈ 1.0×时长**。

| | 当前预估 | 实际 |
|---|---|---|
| 带分离、221 s 的歌 | 20 + 3.75 × 221 = **849 s** | **222 / 226 s** |

高估 3.8 倍。后果是进度条爬得极慢、文案报"粗估还需 14 分钟"而实际 3 分 42 秒就完了 ——
按你们自己定的"不许说谎"标准，这跟 v1.1.3 修掉的那两个假耗时是同一类问题，只是方向相反（这次是虚高）。

**修法**：把 `3.75` 换成 `1.0`（两条干净样本一致），并把 CHANGELOG v1.1.3 里"含分离 3.75×"
那句的取证基础标注为"样本受三任务并发污染，已由 v1.2.0 的串行实测推翻"。
建议顺手把两条样本记进注释：`221.1s → 222.0s / 226.4s`。

### G2（P2）选点定稿直接覆盖 `weights/<name>.pth`，没有备份、也不是原子替换

`rvc_train_promote` 把 `extract_small_model` 的输出直接指向 `RVC_MODELS_DIR/<name>.pth`，
成功判据只有"返回码 0 + 文件存在 + `mtime >= pick.mtime`"。

- 写出半截（磁盘满 / 900 s 超时被杀 / 导出中途崩）时，只要 mtime 更新过就会**被判成功**，
  而 `assets/weights/<name>.pth` 已经是坏的了 —— 音色当场报废，且没有回滚路径。
- 成品约 55 MB（本机 4 个音色 55–58 MB），留一份 `.bak` 的代价可以忽略。

**修法**：导出到 `weights/.promote_<name>_<step>.pth` → 校验体积合理（> 原文件 50%）
且能被 `torch.load`/推理侧加载 → `os.replace()` 原子替换 → 替换前把上一版
`os.replace` 成 `<name>.pth.bak`（只留一版即可）。失败时原文件不动。

### G3（P2）预览小模型会短暂落进 `assets/weights/`，可能被当成音色

`_rvc_small_model` 让 `extract_small_model` 写到 `RVC_MODELS_DIR / (cache.stem + ".pth")`
（即 `assets/weights/G_2333333.pth`），再 `shutil.move` 到缓存目录。而

```python
def _rvc_models() -> list[str]:
    return sorted(p.name for p in RVC_MODELS_DIR.glob("*.pth"))
```

于是**这期间音色下拉框会多出一个 `G_2333333`**；600 s 超时或中途崩溃时，这个文件会永久留在
权重目录里、被列成一个可选音色（它其实是能推理的小模型，所以不会报错，只会悄悄多一个"杂音色"）。
目前 `assets/weights/` 是干净的（只有 4 个正式音色），所以还没发生过，属于埋着的坑。

**修法**：给这次导出传一个专用临时目录当 `weight_root`（如 `runtime/rvc/preview_tmp`），
导出完再 `move` 到缓存；`_rvc_models()` 也可顺手跳过 `G_*` / `D_*` 前缀。

### G4（P3）已完成任务的 meta 里还留着排队阶段的字段

两条 03:13 的产物：`status=done`，但 `step="排队中"`、`queue_pos=1/2`。
前端只在 pending 分支读 `step`，所以界面看不出来；但 meta 是诊断与 AI 侧读取的依据，
"已完成"的任务挂着"排队中"会误导事后排查。建议在 `_rvc_mark_running` / 写 done meta 时清掉
`step` 与 `queue_pos`（或只在 pending/running 时写）。
