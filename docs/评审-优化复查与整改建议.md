## P0 · 阻断级：LAN 模式经 dsh 代理后所有请求 403

### 现象
用户开启 `YUE2_ALLOW_LAN=1` + `YUE2_LAN_HOSTS=192.168.1.7` 后，从 `http://192.168.1.7:3081` 打开工作台，
页面与所有接口全部 403，网关等于不可达。

### 根因（两道独立拦截，任一命中即 403）
`dsh-plugin/src/ui-panel.mjs` 的 `proxy()` 把内部跳转发往网关时：

```js
const headers = { ...req.headers, host: `${LAB_HOST}:${LAB_PORT}` };  // LAB_HOST 恒为 '127.0.0.1'
```

即 **Host 永远被强制成 `127.0.0.1:7863`**，并原样转发浏览器的 `Origin`。于是网关守卫
（`app.py :: _guard_local_only`）在 LAN 模式下看到的是：

1. **Host 检查**：`LAN_MODE=True` 时要求 `host ∈ LAN_HOSTS`。但收到的 Host 是 `127.0.0.1:7863`，
   `127.0.0.1` 不在 `LAN_HOSTS`（只有 `192.168.1.7`）→ 所有请求（含 GET）直接 403。
2. **写请求 Origin 检查**：即便绕过上面，写请求的 Origin 是 `http://192.168.1.7:3081`（UI 在 3081），
   而 `_origin_in_allowlist` 只允许端口 `∈ (None, _P_GW=7863)`，`3081` 不在内 → 写请求 403。

### 复现（单元级，不依赖真起服务）
本机用临时脚本 `tmp/_lan_repro.py` 复现过一遍（`tmp/` 在 `.gitignore` 里，**不随仓库分发**）——
把 `app.LAN_MODE=True, LAN_HOSTS={'192.168.1.7'}` 后，用代理真实会发出的请求头调用守卫：

```
[GET ] Host=127.0.0.1:7863       -> 403   (整个网关经代理不可达)
[POST] Origin=192.168.1.7:3081   -> 403   (UI 所有写操作被拒)
[POST] Origin=192.168.1.7:7863   -> 200   (现有测试覆盖的"直连网关"假路径)
```

**关键：第三行正是现有测试 `test_lan_mode_allows_only_whitelisted_host_and_port` 走的路径**——
它把 `TestClient` 的 `base_url` 直接设为 `http://192.168.1.7:7863`，所以 Host/Origin 端口都是 7863，
压根没经过代理的 `Host` 改写。**测试架构与真实架构脱节，导致假绿。**

### 修复建议（两处，缺一不可）
网关 `app.py`：

```python
# 1) Host 检查：LAN 模式下放行"白名单主机"或"回环"。
#    回环必须放行——网关永远只通过 3081 代理以 127.0.0.1:7863 打到本机，
#    外部攻击者无法伪造一个打到 lanhost:7863 的请求却把 Host 写成 127.0.0.1。
if LAN_MODE:
    if _host_name(host) not in LAN_HOSTS and not _host_is_loop(host):
        return JSONResponse(status_code=403, content={"detail": "主机名不在局域网白名单内"})
elif not _host_is_loop(host):
    return JSONResponse(status_code=403, content={"detail": "只接受面向本机回环地址的请求"})

# 2) 写请求 Origin 检查：LAN 模式下 UI 在 dsh 端口(:3081)，允许网关端口或 dsh 端口
def _origin_in_allowlist(value: str) -> bool:
    ...
    return h in LAN_HOSTS and u.port in (None, _P_GW, _P_DSH)
```

> 为什么放行回环 Host 是安全的：网关在 LAN 模式下对外的真实身份由 `Origin/Referer`（浏览器原始来源）
> 表达，Host 是代理内部跳变的。外部攻击者直接打 `lanhost:7863` 时 Host 是 `lanhost:7863`（∈白名单）；
> DNS 重绑定的 `Host: evil.example` 仍被拒。回环 Host 仅来自本机代理，已可信。

## P1 · 重要

### P1-1 集成测试未覆盖代理路径（假绿的根因）
`tests/test_review_fixes.py` 的 LAN 用例用 `TestClient(base_url="http://192.168.1.7:7863")` 直连网关，
没有走 `ui-panel.mjs` 的代理。建议新增一个**代理集成测试**：起一个最小 http server 套用 `proxy()` 的
请求构造（强制 `host:127.0.0.1:7863`、原样带 `Origin`），再对网关跑 GET/POST，断言 200/403 符合预期。
这样 P0 不至于下次被改回去。

### P1-2 LAN 模式下 CORS `allow_origins` 仍是回环
`app.py` 的 `CORSMiddleware` 的 `allow_origins` 写死回环两个端口，LAN 模式下若用户直接在浏览器开
`http://192.168.1.7:7863`，响应会被 CORS 挡（无 `Access-Control-Allow-Origin`）。
当前设计路径是"经 3081 代理、浏览器只跟 3081 说话"，所以 CORS 不参与；但若将来有人直连网关，
体验会莫名其妙。建议 LAN 模式下把 `LAN_HOSTS` 对应的 `http://<host>:<gw>` / `<dsh>` 也加进
`allow_origins`（或在 `LAN_MODE` 下动态扩展）。

### P1-3 非回环绑定但缺名单时，导入期 `RuntimeError` 会引来看门狗崩溃循环
`_resolve_lan_mode` 在 **模块导入时** raise。若运维配错（开了 `YUE2_ALLOW_LAN` 却没给 hosts），
`python -s app.py` 在绑定端口**之前**就崩。看门狗发现端口没起来 → 不断 `spawn_gateway` → 不断崩溃。
错误虽落在 `runtime/data/logs/gateway.err.log`，但看门狗没有"启动即死"的熔断。
建议：看门狗记录子进程"启动后 N 秒内退出"的次数，连续几次直接放弃重启并告警，避免空转刷日志。

## P2 · 优化点（不影响当前回环模式，给后续迭代）

1. **`_id_busy` 的目录扫描成本**：每次 `_new_id()` 都要 `OUTPUT_DIR.glob(rid + ".*")` 再逐个 `.exists()`。
   当前产物 300+ 且持续增长，未来上千后每次生成都全目录扫描。建议：① 产物按日期/前缀分子目录；
   或 ② 维护一个 `{rid: True}` 的内存索引（进程内 `_ID_SEEN` 已有一半，补全即可）。当前无碍，标记待办。

2. **`transcribe_abc(melody_only=False)` 失败即整份空**：已知权衡（文档已说明）。可加一道韧性——
   和弦记号解码（`chord_symbol_to_abc`）失败时，自动回退 `melody_only=True` 而非整份 ABC 失败，
   让用户至少拿到旋律谱。

3. **`models_switch` 拒绝嵌套路径**：`Path(path).name != path` 会把 `model/sub/foo` 判 400。
   若将来支持模型子目录，需放宽（但仍禁止 `..` 与绝对路径）。

4. **守卫中间件给所有响应（含大文件下载、SPA）加 CSP 等头**：逻辑正确但略有冗余开销，
   可对 `application/octet-stream` / 媒体下载响应跳过 `Content-Security-Policy` 设置。

5. **看门狗 90s 深探的代价**：`DEEP_PROBE_TIMEOUT=90` 且 `FAIL_THRESHOLD=5`，重载/高负载下最坏要
   ~7.5 分钟才判定真死。这是 fb24917 为"宁慢勿错杀"做的取舍，方向正确，建议在文档里明示这个窗口，
   避免有人误以为看门狗"卡住"。
