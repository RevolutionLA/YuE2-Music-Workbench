# 常见问题（FAQ）

> 从 README 抽出的问答合集，内容与原 README 完全一致；改行为的 PR 请同时更新这里与 README 的行为描述。


<details>
<summary><b>生成到一半 GPU 显存不够了，能不能接着跑？</b></summary>

能，从 v10.21.1 起生成拆成两段：**先只跑 AR**（拿语义 token + 计划谱，落盘成检查点），
**再渲染 NAR+VAE**。第二段失败（核显上典型是 VAE 分配失败）时检查点会保留：

* 失败卡片上点「↻ 从检查点继续」，或 `POST /api/generate/resume/<任务ID>`；
* 系统按「style/歌词/cot/种子/步数」的哈希找回检查点，**直接跳过 AR**，只重渲染；
* 检查点 7 天过期；成功出一首即删。

实测（Vulkan，96 token）：一次性 193.5 秒；AR 检查点 135.4 秒；**从检查点渲染 20 秒**。
整首几分钟的歌里 AR 占大头，续跑省的就是这一段。**诚实的差异**：续跑的波形与一次性生成
不逐字节相同（同 token、同时长、同语义，RNG 流不同）。CPU 后端不产语义产物，
会自动退回一次性生成（语义都不丢，只是没有检查点）。

核显机器上建议在 `secrets/local_env.bat` 里写 `set YUE2_DISABLE_CPU_FALLBACK=1`：
GPU 分配失败时任务直接失败并提示可续跑，而不是整首重算到慢 14 倍的 CPU 上。

**这个开关从 v10.21.4 起不再依赖启动脚本加载**：网关在进程环境没有该变量时会直接读
`secrets/local_env.bat`。我们踩过的坑是文件被保存成 LF 换行，cmd 把最后一行注释和 `set`
拼成一条命令，开关静默失效，一首长歌在 CPU 上白跑了近 4 小时。`/api/backend/mode` 的
`cpu_fallback_allowed` 和页面模式行（「分配失败不回退 CPU」）会显示当前真实状态。

**分配失败会自动救一次**（v10.21.2）：网关先重启引擎清掉进程内残留的显存分配，
再生一次（有 AR 检查点就跳过 AR）。只有这次还失败才会报错并留给「从检查点继续」。

**任务页重启**（v10.21.3）：队列里失败/取消的条目，卡片上直接有「↻ 重启」；队列正在跑时也
可以点，它只把这一条排回待跑，不打断当前这首。队列栏在跑着且有失败条目时会出现
「↻ 重启失败任务（N）」，一次把当前队列的失败条目排回去。批量条目在第一次派发时就把随机
种子写回队列状态，重试沿用同一个种子——检查点按「style/歌词/cot/种子/步数」哈希，种子一变
就对不上。实测 2026-10-22 03:25：用 01:18 的 5556 token 检查点直接跳过 AR 进入 NAR+VAE。

**阶段进度**（v10.21.5）：任务管理里正在跑的那条会显示「AR 作曲中 / NAR 第 N/M 步（约）/
VAE 解码中」。引擎没有进度回调，网关从引擎日志的 TRACE/TIMING 行判断阶段；NAR 每一步
引擎不写日志，步数是按帧数和步数估算的，所以标了「约」。**NAR 目前不能复用**：VAE 失败时
只有 AR 检查点，重试会重跑 NAR；要省掉 NAR 需要引擎导出 acoustic latent 或提供
`stop_after=nar`，当前版本没有这个能力。

**设置与预检**（v10.21.6）：⑫ 设置里可以直接开关「GPU 分配失败时自动降级到 CPU」，
选择写入 `runtime/data/settings.json`，优先于 `secrets/local_env.bat`。生成任务开跑前会按
歌词/检查点估算 VAE 峰值，明显放不下时 4 秒内直接失败（实测长歌不会启动引擎、不再白等
一小时）；已允许 CPU 回退时改为 warning，先试 GPU、失败再切 CPU。设置页的「本机可用功能」
会列出歌词 TXT、LRC/eLRC、转谱、分离、换声/训练、AI 写词各自是否可用；歌词框和历史任务卡
都可以直接下载歌词 TXT（不依赖 GPU/VAE）。

**⑭ 歌词时间轴与设置收口**（v10.21.7）：新增独立页 ⑭：上传歌曲音频 + 粘贴歌词 → 后台强制
对齐 → 下载 LRC / 逐字 eLRC，不依赖 VAE、不占生成队列。⑫ 设置新增 DeepSeek Key 输入/清除
（写入未入库的 `secrets/deepseek_api_key.txt`）；明暗模式从侧栏移入设置；CPU 回退改成滑块开关；
失败原因在任务框内两行换行，靠近底部的「⋯ 更多」自动向上展开；通知标题优先用歌名
（`task_name`/`batch_name`），不再显示任务 ID 或 Style 首词。
</details>

<summary><b>没有 NVIDIA 显卡能跑吗？</b></summary>

能，而且**先看有没有能用的核显**。没有 N 卡时按 `Vulkan → CPU` 的顺序选后端：

* **核显 Vulkan（首选）**。本机实测（i7-1165G7 + Intel Iris Xe、audio.cpp v0.9.2 的
  `backends: cpu,vulkan` 构建、q4_k_m）：同一条请求，CPU 5,610 秒 → **Vulkan 318 秒（约 14 倍）**；
  3.84 秒片段在 CPU 上 582~672 秒、Vulkan 25~38 秒（15~27 倍）。两边输出**长度与时长完全一致**
  （737,068 字节 / 3.838 秒）、RMS 与峰值同档；逐字节哈希不同属正常（不同 kernel 的浮点舍入）。
  `一键补齐运行件.bat` 会自动下 Vulkan 包并 `--list-devices --backend vulkan` 探一次，
  探到设备才把后端写成 `vulkan`，探不到就退回 `cpu`（同一个包里两个后端都有）。
  注意核显走**统一内存**，跑歌时别同时开大程序；`cpp/audiocpp_server-cpu.exe` 是 CPU 版备份，
  把 `cpp/server.json` 和 `runtime/data/engine_state.json` 的 `backend` 都改回 `cpu` 即切回。
* **VAE 报 3.89GB 分配失败（核显 Vulkan 专属）**：这是 VAE 的**固定解码窗口**
  （sidecar 的 `decode_core_frames=1024` + halo 16）申请的整段缓冲，**不随歌曲变短而变小**。
  在 16GB 核显上运行 `py312\python.exe scripts\set_vae_window.py --frames 512`，脚本会先备份
  sidecar，再改成半窗口；重启引擎/工作台后生效。本机实测 4373 帧的歌用 512 窗口完整跑通：
  27 分钟、174.9 秒 WAV、VAE 分 9 个 tile（约 38 秒）。窗口越小显存越低，但重新拼接次数更多，
  接缝风险更高，改完请完整试听；`--restore` 可恢复官方 1024。
* **只有 CPU 时**，16GB 内存 + 现代多核也能出歌，但等待时间以**小时、乃至天**计。
  实测锚点（纯 CPU、q4_k_m）：66.7 秒的歌 `cot=off + 1 步` 跑了 93.5 分钟（RTF≈84）；
  拆到每阶段是 AR≈0.87 秒/token、NAR≈0.79 秒/帧/步、VAE≈0.47 秒/帧，NAR 随
  `num_inference_steps` 线性放大。一首 3~4 分钟的歌 `full + 8 步`是十几个小时量级、
  `full + 32 步`以天计——想一夜出一首，降步数或缩短歌词段落，别按页面那句 ETA 安排
  （那是按显卡机器标定的）。

三条硬规矩：**笔记本插电**；`cpp/server.json` 的 `busy_timeout_ms` 必须是 `0`（引擎自带的
5 分钟 busy 守卫会把长跑中的请求直接 503 掐断）；`runtime/data/engine_state.json` 的
`backend` 必须与实际构建支持的后端一致（`cuda` / `vulkan` / `cpu`）：枚举值写错会被拒绝；
写了一个构建不支持的后端时，工作台会按 `audiocpp_server.exe --version` 探测到的能力落到可用后端，
并在回包/日志里说明改了什么。出歌期间网关已声明"别进睡眠"（`app.py::_gen_run_once`），但合盖仍可能待机。
诚实的限制：不同机器、不同驱动的 Vulkan 表现可能差很多，同一歌词多次生成波动可达 ±40%，
单点数字本来就不可信，页面因此显示区间而非精确 ETA。

**老安装升级不用手工补这条**：网关启动时会检查 `cpp/server.json`，缺 `busy_timeout_ms` 就备份成
`*.bak-busy-timeout` 再补 `0` 并在日志里说一句；`scripts/setup_runtime.py` 重跑时同样幂等补齐。
显式设成非 0 的只警告、不擅自改（那是用户的显式选择），但会把后果写清楚。
</details>

<summary><b>歌词对齐为什么不是"识别"出来的？</b></summary>

老方案用语音识别（ASR）反推时间轴，但歌声上 ASR 漏识率高达 20-30%（实测错得离谱），误差逐级累积。新方案走**强制对齐**路线：歌词文本是已知的，直接把已知歌词"压"到音频上——中文走 FunASR 字级时间戳，英文走 wav2vec2 CTC 对齐，最后用 VAD 人声起音点做锚点吸附消除集体漂移。字/词级误差在百毫秒量级，同时产出行级 `.lrc` 与逐字 `.elrc`（卡拉OK逐字高亮）。诚实的边界：逐字高亮由**支持 eLRC 的外部播放器**渲染，工作台自己的页面只放音频 + 提供两种下载，不在页面内做逐字滚动。
</details>

<details>
<summary><b>贴了 ABC 乐谱，为什么唱的还是模型自己编的旋律？</b></summary>

乐谱框里有谱 = 按谱生成，这已经不需要你手动配合「规划 CoT」下拉框了：工作台会在提交前**双向**核对口径——**只有旋律声部的谱走 `melody`**（伴奏自由），**带和弦记号的谱走 `full`**（旋律+和声都按谱），档位选反了会被纠正（引擎不会替你改写谱面：`melody` 不会自动删掉谱里的 `"C"`、`"Am7"`，`full` 也不会替你补和声），选了 `off` 同样会被纠正回按谱路线（`off` 带谱会被引擎直接判 400）。之所以要分这两条：外部 ABC 是绕过符号规划器当条件喂进去的，但 `melody`/`full` 是两套不同的原生指令，路线和谱的形态不符就属于口径不符，谱面条件就会走偏——听起来像"没按我的谱唱"。乐谱框下面会实时显示这份谱有没有和弦、将走哪条路线；提交后 toast 提示本次实际路线，历史存档里记的也是实际路线。

「🎸 从参考歌曲提取乐谱」默认给**纯旋律谱**（配 `melody`，翻唱最常用）；勾选旁边的「提取时带和弦」就得到**旋律+和弦完整谱**（配 `full`，和声也一起锚住）。和弦在两种模式下都会被识别，勾选几乎不多花时间。诚实的限制：完整谱的和弦记号要过 SheetSage2 的记号表，遇到它不认的和弦性质会**整份 ABC 导出失败**（不会静默给你一份旧谱，报错里写明原因）——遇到这种情况取消勾选重提一次即可。

注意：按谱生成只锚定旋律走向（`full` 还锚和声），不会保留原曲歌手的音色与原编曲。
</details>

<details>
<summary><b>任务重名了怎么分清是哪一次？队列名字为什么和这次提交的不一样？</b></summary>

每个任务都有一个**全局唯一 ID**（形如 `20260926_183413_64c31a01`：创建时刻 + 32 位随机），任务名可以随便重复，ID 不会。它同时就是落盘文件名（`runtime/output/<ID>.wav/.json/.lrc`、换声与音色训练目录、乐谱存档），所以报障、删除、重跑都能精确定位到一次任务，不会误伤同名兄弟。历史页/换声列表/音色训练卡片/生成进度条上都直接显示 ID，点一下即复制。

批量队列另有**一层队列 ID**，代表"一次提交"：投 2 首就是这 2 首的队列，面板只显示这一批的 `完成/总数`，之前跑过的条目单独计为"历史队列记录"，不再混进当前总数。往**还在跑**的队列里追加时，新任务沿用那支队列的名字和 ID（追加本来就是同一支队列的延伸）。
</details>

<details>
<summary><b>音色训练中断了要重来吗？</b></summary>

不用。音色制作支持断点续跑，中断后从上次进度继续；训练前有模型体检（提前发现权重损坏/不匹配），训练过程支持试听，多音色还能融合。体检要真的把 `.pth` 用 torch 加载一遍（几十秒起步），所以结果按"文件指纹（修改时间 + 大小）"缓存：同一个没动过的模型重复点不会反复重载，重训覆盖了模型则自动失效，需要强制重测就带 `?force=1`；加载失败（损坏、内存不够）不缓存，下次仍会重测。
</details>

<summary><b>歌词/曲风/乐谱能贴多长？超长会怎样？</b></summary>

上限分别是：曲风描述 2,000 字符、歌词 20,000 字符、ABC 乐谱 20,000 字符。超限**直接报错并写明长度与上限**，不再静默截断——以前超长会被砍尾，产出的音频与歌词尾部对不上，强制对齐就会错位，而且你从界面上看不出来被砍过。批量队列按同一口径逐条校验，一条超限只拒那一条。

<details>
<summary><b>删一个任务会带走哪些文件？</b></summary>

按任务 ID 精确清：`runtime/output/<ID>` 的 `.wav/.json/.txt/.lrc/.lrcjob/.elrc` 全套产物、换声任务的工作目录 `runtime/rvc/jobs/<ID>/`（用户上传的原曲与分离出的干声/伴奏，以前只删成品 wav，这些目录会攒成几个 GB 的孤儿）。队列记录与历史存档同步删除。只认这张白名单后缀，**绝不按通配匹配**——把 `*` 当 ID 传进来清不掉任何东西。文件被播放器占用时删不掉就保留，不会假装删除成功。
</details>

<details>
<summary><b>能不能挂到局域网/公网上给别人用？</b></summary>

不建议，而且默认会被拒。网关**只监听 127.0.0.1**，并有一道本机接口守卫：`Host` 不是回环地址直接 403（DNS 重绑定拿到的 `Host: evil.com` 就是这一条挡的）；变更类请求（POST/PUT/PATCH/DELETE）带的 `Origin`/`Referer` 不是本机来源也 403（浏览器 CORS 只挡"读回包"，挡不住"发请求"，任意外部网页都能对 127.0.0.1 发无 body 的 POST 停任务、杀引擎）。响应还会带上 CSP `frame-ancestors` 只允许本机来源内嵌，防点击劫持。

如果你把 `settings.app_host` 改成 `0.0.0.0`（或任何非回环地址）想开放局域网，**网关会直接拒绝启动**并说明原因。两个原因：一是 Host 检查不改的话，局域网请求会被全部 403，"以为开放了其实锁死"比启动即失败更难查；二是放宽后的判定必须还能把"你自己的设备"和"被 DNS 重绑定指到你内网 IP 的网页"区分开——只比较 `Origin` 与 `Host` 这两个都由攻击者域名决定的字符串，等于没判。所以开放要两个变量一起给：`YUE2_ALLOW_LAN=1`（表明你知情）+ `YUE2_LAN_HOSTS=192.168.1.7`（逗号分隔的主机名白名单，就是你实际访问用的那个 IP 或主机名）。只给前者仍然拒绝启动。开放后：`Host` 必须命中白名单或为本机回环（dsh 代理的内部跳变恒发 `Host: 127.0.0.1:7863`），变更类请求的 `Origin` 必须命中白名单**且端口是网关或工作台服务端口**，CSP `frame-ancestors` 与 CORS 也只放行这批主机。局域网模式下没有任何账号隔离，且报错详情会带本机绝对路径与账号名，前面必须自己加一道反代鉴权——本工作台不为公网多用户设计。

⚠️ 一个 TCP 层的坑（评审复查实测确认）：`app_host` 要填 `0.0.0.0`，**不要**填某个具体 LAN IP（如 `192.168.1.7`）。本机 dsh 工作台的内部代理硬编码连 `127.0.0.1:7863`，网关只绑具体 IP 时回环上没人监听，工作台会直接连不上（ECONNREFUSED），HTTP 守卫修得再对也到不了那一层。绑 `0.0.0.0` 才能同时服务回环与局域网；网关启动时会检测到这种配法并打 ⚠️ 警告。

顺带一条同类收口：切换模型（`POST /api/models/switch`）以前"校验用一个变量、写进 `server.json` 用另一个未校验的变量"，`../` 能把路径带出引擎工作目录；现在只接受 `model/` 下的**纯文件名**，带目录的一律 400。
</details>

<details>
<summary><b>启动脚本里 set 的环境变量，网关到底收不收？</b></summary>

收——现在才叫真的收。早期版本首启用 WMI `Win32_Process.Create` 拉起网关（为了不弹黑窗口），而 WMI 派生的进程继承的是 WMI 服务的环境、**不是**那个 cmd 的环境，于是 `HF_ENDPOINT`/`HF_HOME`/`TORCH_HOME`/`FFMPEG_PATH`/`NO_PROXY` 和 `secrets\local_env.bat` 里的密钥对首启进程全部无效；偏偏看门狗重启那条路是带着环境传的，造成"第一次跑的和重启后跑的不是同一套配置"。现在两条路统一为 `Start-Process -WindowStyle Hidden`：同样不弹窗口，但逐层继承父进程环境（实测对照：同一段探针子进程，WMI 读不到变量、Start-Process 读得到）。密钥依旧只走环境继承，绝不出现在命令行字符串里（命令行全局可读）。
</details>
