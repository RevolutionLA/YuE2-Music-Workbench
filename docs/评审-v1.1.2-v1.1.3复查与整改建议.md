### 3. 锁序检查（这块最容易写出死锁，专门过了一遍）
涉及四把锁：`_RVC_LOCK`（任务字典）、`_RVC_QUEUE_LOCK`（队列）、`_GPU_SEM`（显存）、
`threading.Thread` 起停。实际存在的嵌套只有一条：

- `history_active` / `rvc_active`：**持有 `_RVC_LOCK` → 取 `_RVC_QUEUE_LOCK`**（`_rvc_live`）

反向（`_RVC_QUEUE_LOCK` → `_RVC_LOCK`）**不存在**：`_rvc_queue_loop` 在锁内只做"出队 + 写
`_RVC_CURRENT`"，任务体（`_rvc_convert_worker` → `_rvc_mark_running`）一律在锁外执行；
`_rvc_submit` 也在返回前就放了队列锁，调用方才去拿 `_RVC_LOCK`。**无环，不会死锁。**
`_GPU_SEM` 的两处获取是**前后各一次、不嵌套**（分离一次、推理一次），`Semaphore(1)` 非重入也不成问题。

## 二、F1（P1）静音门内存随时长线性暴涨

### 现象
`app.py :: _gate_envelope` 为了算逐帧 dB，把每一帧都切片后 `np.stack` 成一个
`(帧数 × 窗长)` 的 **float64** 二维数组：

```python
frames = np.stack([mono[s:s + n] for s in starts]).astype(np.float64)
```

内存 = 时长 × 采样率 / hop × 窗长 × 8 B ≈ **1.77 MB / 秒音频**（44.1 kHz）。实测：

| 音频时长 | 峰值内存 | 耗时 |
|---|---|---|
| 221 s（= 取证用的那首歌） | **391 MB** | 0.66 s |
| 600 s（10 分钟） | **1061 MB** | 1.88 s |

### 为什么这条要按 P1 处理
- 这段代码跑在**网关进程内**。本机有 OOM 前科（CHANGELOG 里 `19769b4` 的 df77 OOM），
  `app.py` 里那套 `_commit_headroom_mb()` / `_require_headroom_for_preview()` 闸门正是为此而设 ——
  而这道新增的 1 GB 尖峰**完全绕过所有既有闸门**（它不在试听路径上、也不在生成路径上）。
- 触发条件是"换声一首 10 分钟以上的歌"，属于正常用户操作，不是极端输入。
- 换声任务现在还会和生成/训练抢显存，网关进程被 OOM 会连带打断所有在跑的任务。

### 修法（已实测，直接可用）
别用 `np.stack` 展开。分块（每 4096 帧一块）算完写回：

```python
def _frame_db(mono: "np.ndarray", n: int, hop: int, starts: "np.ndarray") -> "np.ndarray":
    """逐帧 RMS dB。分块计算：内存 O(块大小 × 窗长)，不随音频长度线性增长。"""
    import numpy as np
    out = np.empty(len(starts), dtype=np.float32)
    bs = 4096
    for i in range(0, len(starts), bs):
        blk = np.stack([mono[s:s + n] for s in starts[i:i + bs]]).astype(np.float32)
        out[i:i + bs] = 20 * np.log10(np.clip(np.sqrt((blk ** 2).mean(axis=1)), 1e-12, None))
    return out
```

同一条 600 s 音频的对照实测：

| 实现 | 峰值内存 | 耗时 |
|---|---|---|
| 现状（`np.stack` + float64 全展开） | 1061 MB | 1.88 s |
| `sliding_window_view`（只去拷贝，仍整块 `v*v`） | 423 MB | 0.17 s |
| **分块 4096（推荐）** | **44 MB** | **0.59 s** |

顺带把 `.astype(np.float64)` 去掉：dB 计算用 float32 精度完全够（`1e-12` 下限本就是 240 dB 的余量）。

### 验收判据
`tracemalloc` 量 `_gate_envelope` 在 600 s / 44.1 kHz 输入下的峰值 < 100 MB，且
`TestRvcGateAndMix` 7 例不变绿。

## 三、F2 / F3（P2）两处"侥幸安全"

### F2：`_rvc_cancel` 手写的目录删除，守卫比 `_rvc_job_purge` 弱

现成的 `_rvc_job_purge()`（`app.py:1258`）校验齐全：`basename` + 拒绝 `.`/`..` + `.resolve()`
+ `d.parent != RVC_JOB_DIR.resolve()` 才删。

而 `rvc_cancel` 里又手写了一遍：

```python
d = RVC_JOB_DIR / rid
if d.is_dir() and d.parent == RVC_JOB_DIR:
    shutil.rmtree(d, ignore_errors=True)
```

实测 Path 语义 —— 这道守卫对 `".."` 是**放行**的：

```
(base/'20260101_000001_ab').parent == base  → True   （正常，该删）
(base/'..').parent                 == base  → True   （放行！rmtree 会删掉整个 runtime/rvc）
(base/'.').parent                  == base  → False
```

现在靠前面 `_RVC_JOBS.get(rid)` 拿不到 `".."` 而 404 兜住 —— 是侥幸，不是设计。
**修法**：删掉这三行，改成一行 `_rvc_job_purge(rid)`，与 `generate_delete` 共用同一套已审过的校验。

### F3：删除排队中的换声任务，队列里的参数元组不会一起摘掉

`DELETE /api/generate/{rid}` 只对"当前生成任务"做 running 拦截，命中后
`_rvc_job_purge(rid)` 成功就返回 200 —— 但 `_RVC_QUEUE` 里那份
`(rid, job, src, in_dir, ...)` 参数元组原封不动。轮到它出队时 `src` 已被删掉，
RVC 子进程失败 → 该任务以 `error` 状态**重新出现在列表里**（删了又活）。

目前 UI 点不到：`renderHistory` 对 `h.status === "pending"` 不渲染「⋯ 更多」菜单，
所以这是 API 层面的洞，不是用户可见的 bug。

**修法**（二选一）：
1. `generate_delete` 命中 RVC 目录时，先 `if _rvc_cancel(rid): ...` 出队再删；或
2. 命中时若该 rid 在 `_RVC_JOBS` 里且 `status == "pending"`，直接 `409 "排队中，请先在换声页取消"`。

配套补一例测试：排队中的任务被删除后，`_RVC_QUEUE` 里不再有它。

## 五、附带观察（非缺陷，可选优化）

- **任务管理页缺少取消入口**：排队中的换声任务在「历史 / 任务管理」页只有状态文案
  （`⏳ 排队中（第 N 位）`），「⋯ 更多」菜单对 pending 不渲染，取消按钮只在「换声」页有。
  用户在任务管理页看到排队条目却没法取消，得自己切页。建议 pending 时挂一个「✕ 取消排队」。
- **`rvc_active` 的排序键**：`(status != "running", ts)` 用提交时间升序近似队列顺序，
  与 `_rvc_live()` 实时算出的 `queue_pos` 在极端情况下（时钟回拨 / 同一秒提交）可能不一致；
  前端 `renderRvcList` 已经按 `queue_pos` 重排，服务端这个排序被覆盖，不影响观感，可留。
- **`tool_rvc_convert` 的 hint** 已改成"第 N 位"口径，但没提"取消"这个动作；
  可在 `ahead > 0` 时补一句"（可在换声页取消排队）"，避免 AI 侧只能干等。
